# 进阶策略 4：事件驱动策略（Event-Driven）· backtrader 本地版

> 类型：另类策略 / 事件驱动 ｜ 难度：★★★★☆
> 前置知识：`event_calendar` 数据结构、PanelStrategy、事件窗口判断、`live()` 停牌过滤
> **运行框架：backtrader（本地回测 + 免费数据）** ｜ 本策略的**聚宽云端版**见 [docs/joinquant/advanced/04_event_driven.md](../../joinquant/advanced/04_event_driven.md)

## 一、核心思路

前几篇都是"连续因子"（每天都能算动量/波动）。本篇换成"**离散事件**"：有些机会只在特定时点出现——比如财报发布。

事件驱动的核心假设：业绩超预期的公司在**公告后的一段窗口内**，股价倾向于延续上涨（业绩动量 / 分析师滞后反应）。策略围绕"业绩公告"交易：

```
公告后窗口内持有 → 窗口结束自然退出（下一次调仓不再入选 → 被卖出）
没有事件 → 空仓等待（事件驱动的典型特征：不持续持仓）
```

数学表达（事件筛选）：

```
净利润增长率 > THRESHOLD（如 30%）  → 记为"好事件"
事件有效窗口 = [推定公告日 - 0, 推定公告日 + window_days]（自然日）
```

给新手的直觉：平时空仓"等待猎物"，财报季里专挑"业绩炸裂"的公司短线持有，赚的是**事件冲击的定价偏差**，不是长期趋势。

本策略参数一览（文件顶部常量）：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `START` | `2018-01-01` | 回测起点（财务数据 2015 年起，取较长窗口） |
| `UNIVERSE_SIZE` | `40` | 沪深300 前 40 只成分股 |
| `TOPN` | `10` | 同时最多持有事件股数 |
| `THRESHOLD` | `30.0` | 净利润增长率 > 30% 才算"好事件" |
| `EVENT_WINDOW` | `25` | 事件有效窗口（自然日） |
| `ANNOUNCE_LAG` | `45` | 报告期 → 推定公告日的滞后天数 |

聚宽版是"未来 10 天将披露财报即买入、持有 5 交易日卖出（每日运行）"；本地版改为"周度重算、窗口 25 自然日、用报告期 + 45 天近似公告日"。

## 二、算法结构（分步拆解）

```
__init__()：event_calendar(codes, threshold, lag_days=45) 预建事件日历
   │
   └─ 每周 next()（PanelStrategy weekly）→ on_rebalance(cur)
         │
         ├─ 1. lo = cur - window_days（窗口下界，自然日）
         │
         ├─ 2. 遍历 calendar：code 在 datas 且 live(d,cur) 且
         │      存在事件 (lo <= 推定公告日 <= cur) → 加入 active
         │
         ├─ 3. active 为空 → close_all（空仓等待）
         │
         └─ 4. active 非空 → equal_weight_order(active[:topn], cur)
```

## 三、代码逐段详解 + backtrader 语法解析（本篇重点：事件日历）

### 3.1 `event_calendar` 的数据结构

`__init__` 里一次性预建好整段历史的事件日历：

```python
self.calendar = event_calendar(codes, threshold=self.p.threshold,
                               lag_days=ANNOUNCE_LAG)
```

`btlab.runner.event_calendar` 返回的结构是：

```
{代码(str): [(推定公告日(pd.Timestamp), 指标值(float)), ...], ...}
```

- key 是股票代码，value 是"该股票所有好事件"的列表，每个事件是一个 `(公告日, 指标值)` 二元组。
- 只保留"净利润增长率 > threshold"的事件（`event_calendar` 内部 `s = s[s > threshold]`）。
- 本例输出：37 只股票有"好事件"，合计 518 次（日志可见）。

一个构造后的真实片段（示意）：

```
{
  '600000.SH': [(Timestamp('2024-02-14'), 45.3), (Timestamp('2024-08-30'), 38.1)],
  '000001.SZ': [(Timestamp('2024-04-20'), 52.7)],
  ...
}
```

每个 `Timestamp` 都是"报告期 + 45 天"推出的，**绝不晚于真实可见日**。

### 3.2 公告日的"近似"——防未来函数的关键

聚宽能查财报的**实际公告日**；本地免费源（新浪财务）只有**报告期**（如 2023-12-31 的年报）。真实世界中，1 月 1 日不可能知道去年 12 月 31 日的年报数据。所以这里用"报告期 + 45 天"推断公告日：

```python
cal[str(c)] = [(d + pd.Timedelta(days=lag_days), float(v))
               for d, v in s.items()]
```

`lag_days=45` 是"季报/年报通常在报告期结束后约 1~1.5 个月才披露"的经验值。这是教学简化，会让事件窗口**有偏移**——真实公告日可能更早或更晚。聚宽版用 `get_fundamentals` 的 `report_date` 字段能拿到真实公告日，这是两版最大的数据差异。

一个"推公告日"的具体例子：某公司 2023 年报报告期为 `2023-12-31`，加 45 天滞后 → 推定公告日 `2024-02-14`。若回测进行到 `2024-02-20`，则 `lo = 2024-02-20 - 25天 = 2024-01-26`，判断 `2024-01-26 <= 2024-02-14 <= 2024-02-20` 成立 → 该股"仍在窗口内"，会被买入。注意推定公告日 `2024-02-14` 在 2024-02-20 之前，用的是**已发生**的日期，没有看未来。

### 3.3 "在窗内"判断

`on_rebalance` 里判断某股票当前是否有"有效事件"：

```python
lo = pd.Timestamp(cur) - pd.Timedelta(days=self.p.window_days)
active = []
for code, events in self.calendar.items():
    if code not in set(self.getdatanames()):
        continue
    d = self.getdatabyname(code)
    if not self.live(d, cur):            # 停牌不参与
        continue
    if any(lo <= dt <= pd.Timestamp(cur) for dt, _ in events):
        active.append(code)
```

- `lo` 是窗口下界（当前日往前 `window_days` 个自然日）。
- `any(lo <= dt <= cur)`：只要该股票有任意一次"推定公告日"落在 `[lo, cur]` 区间内，就视为"事件仍在窗口内"。
- 关键：判断用的是 `dt <= cur`（推定公告日不晚于今天），**绝不看未来**——这正是防未来函数。若写成 `dt > cur`（等未来公告）就是泄漏。
- `self.live(d, cur)` 过滤停牌；`code not in getdatanames()` 过滤数据缺失股票。

### 3.4 空仓也是一种仓位管理

```python
if not active:
    self.close_all(cur)                  # 没有事件 → 空仓等待
    return
self.equal_weight_order(active[:self.p.topn], cur)
```

事件驱动策略**不持续持仓**：没有好事件就清仓观望。这与动量/轮动"永远满仓某组标的"形成鲜明对比。`equal_weight_order` 最多持有 `topn=10` 只（骨架内部 `round_lot` 整手）。

### 3.5 `PanelStrategy` 与索引方向

- 继承 `PanelStrategy`，`rebalance='weekly'`（调度用 `isocalendar()[:2]` 周号）。
- `window_days=25` 是**自然日**窗口，但调仓是**周度**，所以事件会在"公告后约 1~3 次调仓内"持续入选，窗口结束自然退出。
- 全程只用 `self.live`（历史对齐）+ 预建日历（已滞后 45 天），无 Line 正索引，无未来函数。

### 3.6 为什么"周度重算"而不是"每日买入持有 N 天"

聚宽版是"每日发现未来披露事件 → 买入 → 持有满 5 交易日卖出"。本地版改为每周重算"推定公告日是否落在窗口内"：只要事件还在 `[lo, cur]` 内，下周仍会被选中（持续持有）；窗口一过（推定公告日早于 `lo`），下次调仓不再入选 → 自动被 `equal_weight_order` 卖出。这样做的好处是**免维护 `buy_date` 字典**、逻辑更声明式，且天然处理"事件重叠/连续事件"；代价是调仓粒度变粗（周级），事件脉冲可能被平滑掉一些。

### 3.7 事件日历在 `__init__` 预建的代价

`event_calendar` 在 `__init__` 里对全部 38 只股票逐一拉财务数据、筛"好事件"，日志提示"首次较慢"——因为单次构建要发几十次网络请求。但它是**一次性**的：建好 `self.calendar` 后，每根 K 线的 `on_rebalance` 只是查字典，不再联网，回测主循环很快。这正是"重活放 `__init__`、轻活放 `next()`"的工程习惯：初始化慢一点没关系，逐根循环必须快。

### 3.8 "净利润增长率 > 30%"只是最朴素的事件代理

聚宽版想抓的是"业绩**超预期**"（实际业绩高于市场一致预期），这是事件驱动里更严谨的因子。但免费源拿不到"分析师预期"，本例退而求其次，用"净利润增长率 > 30%"作**代理**：高增长通常伴随正面惊喜，且数据可得。代价是它分不清"增速高但低于预期"（其实是坏事件）和"增速高且超预期"（好事件），会引入噪声。更严谨的做法是接盈利预期数据，或改用"单季环比加速""营收+利润双升"等复合条件（`event_calendar` 的 `field` 参数可换）。

### 3.9 `window_days` 用"自然日"而非"交易日"的含义

`lo = cur - pd.Timedelta(days=25)` 减的是**自然日**（25 个日历日 ≈ 18 个交易日）。因为调仓是**周度**的，25 自然日窗口 ≈ 3~4 次调仓。也就是说一只"好事件"股通常在公告后约 1 个月内持续入选、被持有，窗口一过自然退出。如果想让窗口更紧凑（只吃公告后第一波脉冲），把 `EVENT_WINDOW` 调小到 10~15 自然日即可；调大则事件动量被更多噪声稀释。

### 3.10 空仓也是一种仓位管理（回看核心思路）

再次强调：事件驱动策略**不持续持仓**。某些月份若没有任何股票的"好事件"落在窗口内，`on_rebalance` 会走到 `close_all(cur)` 直接空仓观望。这跟动量/轮动"永远满仓某组标的"形成对比——事件策略的收益来自"精准命中少数事件"，而非"长期暴露在市场中"。所以本策略的换手率（8078%）虽高，但很多月份是"空仓→小仓位"的切换，整体暴露其实低于看似满仓的策略。

## 四、与聚宽版的差异

| 维度 | 聚宽云端版 | backtrader 本地版 |
|------|-----------|-------------------|
| 事件日 | `get_fundamentals` 查 **实际 report_date**（真实公告日） | 只有**报告期**，用"报告期 + 45 天"**近似公告日**（有偏移） |
| 触发方式 | `run_daily(trade, time='09:30')`（每日） | `PanelStrategy` 周度（`weekly`） |
| 持有方式 | 买入后记 `buy_date`，持有满 `hold_days=5` 交易日卖出 | 每周重算"在窗内"，窗口结束自动退出 |
| 持仓上限 | `stock_num=20` | `topn=10` |
| 事件筛选 | 未来 10 天将披露财报即视为事件 | 净利润增长率 > 30% 且"推定公告日落在窗口内" |
| 下单口径 | `order_target_value(security, 市值)` | `equal_weight_order`（目标股数，整手） |
| 数据来源 | 聚宽财务表 | akshare 新浪财务（报告期口径） |

最大差异是**事件日精度**：聚宽用真实公告日（无偏移），本地用报告期 + 45 天近似（会偏移几天到几周）。这会让本地版的事件窗口"迟到"，是教学简化的已知代价。

## 五、回测结果（真实数据）

区间 2018-01-02 ~ 2026-09-30（2123 个交易日），初始资金 100 万元，基准沪深300。数据来自 `results/logs/bt_a04_event_driven.log`。

| 指标 | 数值 |
|------|------|
| 累计收益率 | 17.69% |
| 年化收益率 | 1.95% |
| 基准累计收益率 | 6.61% |
| 超额收益 | 11.08% |
| 最大回撤 | -27.40% |
| 夏普比率 | 0.22 |
| 年化波动率 | 12.05% |
| 日胜率 | 50.67% |
| 总成交笔数 | 1281 笔 |
| 累计换手率 | 8078.50% |

解读：事件驱动跑赢沪深300（超额 +11.08%），但绝对收益不高（年化 1.95%）、夏普仅 0.22、波动 12.05% 偏高。说明"业绩超预期"事件在 A 股有一定超额（尤其相对弱基准），但事件窗口短、调仓频繁（1281 笔、换手 8078%）导致摩擦成本大，且公告日近似偏移削弱了其有效性。回撤 -27.40% 中等——事件策略本就不追求低回撤，赚的是"事件脉冲"而非稳健。

## 六、改进方向（思考题）

1. **更细的事件源**：除净利润增长率外，叠加业绩预告、快报、分析师上调评级等多源事件（`event_calendar` 可扩展 field），提高事件命中质量。
2. **精确公告日**：若后续接入能查真实公告日的源，去掉 "+45 天"近似，事件窗口会更准，回测更贴近实盘。
3. **事件后止损**：对单只事件股加 `buy_bracket` 止损腿，防止"业绩好但股价反跌"的暴雷；并把窗口从固定 25 天改为"公告后 N 交易日"的动态窗口，减少噪声混入。
