## 一、这一篇你将学到什么

前面所有策略都是"**持续持仓**"（每个月总有仓位）。这一篇第一次做**不连续持仓**：**没有事件就空仓。**

| 你会搞懂 | 一句话 |
|---|---|
| **事件驱动** | 不按因子排序，而是按"发生了什么事"选股 |
| `event_calendar()` 的数据结构 | `{代码: [(日期, 指标值), …]}` |
| **事件窗口** | 公告后 N 天内才算"新鲜事件" |
| 空仓纪律 | 没有事件就不硬凑仓位 |
| 报告期 ≠ 公告日 | 免费数据只有报告期，要用"报告期 + 45 天"近似 |

**读完你应该能回答**：为什么这个策略大部分时间可能是空仓？这对绩效意味着什么？

## 二、心智模型：只在"刚发财报"后买

```
每周第一个交易日（收盘后）
   │
   ├─ 1. 看日历：过去 25 个自然日内，有哪些股票公布过"净利润增长率 > 30%"？
   │
   ├─ 2. 有 → 等权买入这些股票（最多买 10 只）
   │      没有 → 清仓（!）
   │
   └─ 3. 窗口过期（超过 25 天）→ 自动不再入选 → 被卖出
```

**时间轴示例**：

| 日期 | 事件 | 动作 |
|---|---|---|
| 8/14 | 某公司公告（报告期 6/30 + 45 天） | 进入日历 |
| 8/15（周一） | 调仓日 | 发现事件 → 买入 |
| 9/1 | 调仓日 | 事件仍在 25 天窗口内 → 继续持有 |
| 9/10 | 调仓日 | 已过 25 天 → 不再入选 → 卖出 |

> **关键理解**：这个策略天然是"**低频、间歇性持仓**"的。如果某段时间没有公司发布超预期财报，它就**空仓等待**——这不是 bug，是事件驱动策略的典型特征。

---

## 三、核心思路

**事件驱动（Event-Driven）**：价格对信息的反应不是一瞬间完成的，而是**逐渐消化**（学术上叫"财报后漂移"，PEAD）。

**策略假设**：业绩超预期（净利润高增长）的公司，在公告后的一段时间里**继续跑赢**。

**两个关键参数**：

| 参数 | 含义 | 本策略取值 |
|---|---|---|
| `THRESHOLD` | 什么算"超预期" | 净利润增长率 > **30%** |
| `EVENT_WINDOW` | 事件有效期 | 公告后 **25 个自然日** |

**关于"公告日"的数据问题（重要）**：

免费数据源（新浪财经）只提供**报告期**（3/31、6/30、9/30、12/31），**没有公告日**。真实世界里：

| 报告期 | 真实公告日 |
|---|---|
| 一季报（3/31） | 4 月中下旬 |
| 半年报（6/30） | 8 月 |
| 三季报（9/30） | 10 月下旬 |
| 年报（12/31） | 次年 1~4 月 |

本策略用 **报告期 + 45 天** 作为"推定公告日"的近似。**这是教学用简化**——真实的公告日可以（也应该）用聚宽的历史公告日数据。用报告期本身就是未来函数（1 月 1 日你不可能知道 12 月 31 日的年报数据）。

## 四、算法结构

```
main() → load_index_members → load_universe → __CAL__ → run_strategy
   │
   └─ EventDriven.__init__()
         └─ self.calendar = event_calendar(codes, threshold=30, lag_days=45)
               → { 'sh600036': [(2018-05-15, 35.2), (2018-08-14, 41.0), ...], ... }
   │
   └─ 每周 on_rebalance(cur)
         ├─ lo = cur - 25 天
         ├─ 遍历日历：本股票 live() 且存在事件 dt ∈ [lo, cur] → active
         ├─ active 为空 → close_all()（空仓）
         └─ 否则 → 取前 10 只 → equal_weight_order()
```

## 五、代码逐段详解

### 5.1 参数与事件日历

```python
UNIVERSE_SIZE = 40
TOPN = 10                   # 同时最多持有的事件股数
THRESHOLD = 30.0            # 业绩超预期阈值：净利润增长率 > 30%
EVENT_WINDOW = 25           # 事件有效窗口（自然日）
ANNOUNCE_LAG = 45           # 报告期 → 推定公告日 的滞后天数

def __init__(self):
    super().__init__()
    codes = [d._name for d in self.tradables]
    self.calendar = event_calendar(codes, threshold=self.p.threshold,
                                   lag_days=ANNOUNCE_LAG)
```

`event_calendar` 内部做的事（btlab 源码逻辑）：

```python
s = pd.to_numeric(df['净利润增长率(%)'], errors='coerce').dropna()
s = s[s > threshold]                                  # 只留"好事件"
cal[code] = [(d + pd.Timedelta(days=lag_days), float(v)) for d, v in s.items()]
#             ↑ 报告期 + 45 天 = 推定公告日
```

**这一步就把"报告期"翻译成了"可用日"**——和策略 5 的 `roe_panel(lag_days=45)` 是同一个思路。

### 5.2 每周判断"有没有新鲜事件"

```python
def on_rebalance(self, cur):
    lo = pd.Timestamp(cur) - pd.Timedelta(days=self.p.window_days)
    active = []
    for code, events in self.calendar.items():
        if code not in set(self.getdatanames()):
            continue
        d = self.getdatabyname(code)
        if not self.live(d, cur):               # 停牌不参与
            continue
        if any(lo <= dt <= pd.Timestamp(cur) for dt, _ in events):
            active.append(code)

    if not active:
        self.close_all(cur)                      # 没有事件 → 空仓
        return
    self.equal_weight_order(active[:self.p.topn], cur)
```

| 代码 | 作用 |
|---|---|
| `lo = cur - 25 天` | 事件窗口的**左边界**（自然日，不是交易日） |
| `lo <= dt <= cur` | 事件必须落在 `[左边界, 今天]` 之间 |
| `if not active: close_all()` | **空仓纪律**：没有事件就不硬凑 |
| `active[:topn]` | 事件太多时只取前 10 只（按日历顺序，不是按强度） |

> **注意 `events` 里的 `dt` 是"推定公告日"**，不是真实公告日。用真实公告日会让策略更准确，也更符合"事件驱动"的原意。

## 六、一次真实运行的轨迹

```
  构建业绩公告事件日历（38 只，首次较慢）...
  共 34 只有"好事件"，合计 152 次
[3/3] 开始 backtrader 回测 ...
```

**"34 只有好事件、合计 152 次"** 这行信息量很大：

- 38 只里只有 34 只曾经"净利润增长率 > 30%"；
- 7 年多一共 152 次事件 ≈ **平均每只 4.5 次**；
- 每次事件只在 25 天窗口内持仓 → **大量时间是空仓**。

## 八、回测结果怎么读

| 指标 | 数值 | 怎么理解 |
|---|---|---|
| 累计收益率 | **+17.69%** | 8 年半只有 17.69% |
| 年化收益率 | **+1.95%** | 很低 |
| 最大回撤 | **−27.40%** | 对"大部分时间空仓"的策略来说偏高 |
| 夏普比率 | **0.22** | 差 |
| 成交笔数 | 1281 | 事件进出频繁 |

**要点：**

1. **收益平平**：事件驱动在 A 股这段历史里没有明显超额；
2. **回撤 −27.40% 值得警惕**：说明"事件股"之间有很强的同涨同跌（比如都是成长股），**分散度不够**；
3. **"取前 10 只"是按日历顺序，不是按超预期强度**——这是一个明显的改进空间；
4. **实际持仓时间很短**：虽然回撤不小，但它是"脉冲式"的风险暴露。

> **教学价值**：这一篇教你处理**离散事件数据**（而不是连续因子），以及"没有信号就空仓"这种**特殊的仓位纪律**。

## 九、易混点与常见错误

| 症状 | 原因 | 正确做法 |
|---|---|---|
| 用了报告期当天 | 那是未来函数 | 报告期 + 滞后天数（近似公告日） |
| 事件窗口算错 | 混用了自然日和交易日 | 本策略用**自然日**（25 天） |
| 没有事件还是满仓 | 忘了 `close_all()` | 无事件必须清仓 |
| 事件股同涨同跌 | 事件股集中在同一风格 | 加行业/风格中性（进阶） |
| 以为 45 天很精确 | 真实公告日因公司而异 | 需要精度就用聚宽的公告日数据 |

## 十一、改进方向（思考题）

1. **按强度排序**：把 `active` 按"超预期幅度"排序（日历里已经存了数值），而不是按代码顺序。
2. **缩短事件窗口**：25 天 → 10 天，看收益是否更集中（PEAD 效应通常在前几周最强）。
3. **加行业中性**：避免事件股全是同一个行业。
4. **叠加止损**：事件股常见"利好出尽"，可以加一个 -8% 的止损。
